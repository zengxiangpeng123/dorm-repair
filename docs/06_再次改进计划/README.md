## 一、为什么重新计划

当前系统已有真实 MySQL、状态机、角色鉴权和完整业务链，但仍包含演示入口、固定身份、占位照片、内存会话、默认数据库口令和未完成的 AI 正式接入。文档中的“测试通过”只证明演示范围可用，不能替代生产验收。

本次改进采用**一次改进一个独立目录**的方式。每个目录均是一次完整的变更流程，包含：

```text
00-变更摘要与现状.md
01-目标与范围.md
02-方案与影响.md
03-实施任务与顺序.md
04-测试与验收.md
05-上线与回滚.md
06-执行记录.md
```

目录中的“目标”不得写成“已完成”；只有实现、测试、部署证据全部归档后，才能修改状态。

## 三、执行纪律

1. 按目录顺序推进，不把多个迭代的改动混成无法回滚的大提交。
2. 每个改动同时更新 API、数据库、权限、测试和部署文档。
3. 每次改进至少形成一个独立提交；不得覆盖上一迭代的执行证据。
4. 禁止提交 `.env`、真实密钥、生产数据、真实学生照片和访问令牌。
5. 未通过测试不得标记完成；未通过生产准入不得宣称可上线。
6. 保留 `docs/04_项目管理/开发计划文件夹` 作为课程演示版的历史计划，不改写历史。

## 四、全局生产准入条件

- 无固定人员身份、默认口令或公开演示重置入口。
- 学生端、师傅端、管理端独立构建与部署，不共享会话、页面、命令或可写身份存储。
- 会话支持过期、撤销和重启恢复；多实例有一致身份。
- 照片真实存储，上传和读取均有权限、类型和大小校验。
- AI 使用真实模型服务，结果可追溯，失败可降级且不会改写历史。
- 学生不能通过旧接口绕过返修审查；关键写操作可幂等。
- 有数据库备份恢复、HTTPS、日志、指标、告警和资源限额。
- 试点运行无致命/严重缺陷，完成安全、性能和容灾验证。
