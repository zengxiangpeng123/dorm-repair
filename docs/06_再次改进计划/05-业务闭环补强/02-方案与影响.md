# 02 方案与影响

## 目标方案

- 禁用旧 `/orders/{no}/reject` 的直建子单能力；新流程只走申请与管理员审查。
- 对提交、派工、到门、完工、申请、审查、撤销、配置等写操作实现 `Idempotency-Key`。
- 新增幂等记录：actor、方法、规范化路径、key、request_hash、response、status；同 key 不同内容拒绝，重复请求返回首次结果。
- 审查使用 attemptNo 保留历史，reworkIndex 批准时分配；重复审查不生成第二张子单。
- 第 2 次返修批准写入 `REPEAT_REWORK`；最终验收关闭原单及所有 `REWORKING` 前序单。
- 正式实现管理员对维修中撤销申请的决定、原因、事务与权限；不能再用 501 作为长期业务方案。
- 评估并补齐人员、楼栋、工单、照片、审查、例外等必要外键或一致性巡检。

## 影响清单

| 层面 | 改动 |
|---|---|
| 后端 | 命令入口、幂等拦截、返修/撤销事务、异常与权限 |
| 数据库 | 幂等表、撤销决定字段、约束与一致性检查 |
| API | 旧接口废弃、幂等头、撤销决定 DTO 与错误码 |
| 前端 | 重试复用 key、重复提交禁用、撤销处理界面 |
| 部署 | 迁移、幂等清理、监控与历史数据兼容 |

## 兼容与回滚

先迁移并双写，再切换；回滚保留幂等、审查和审计数据，不删除历史记录。

## 风险

唯一键冲突、事务长锁、重复响应、旧客户端误用、历史孤儿数据、级联关闭遗漏。
