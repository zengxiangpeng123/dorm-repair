## 三、写得好的地方

### 3.1 文档体系比较完整

项目已经形成“需求—统一口径—流程图—接口—总体设计—开发计划—测试—用户手册—答辩—再次改进”的材料链。特别是 CG01–CG14 编号清晰，基本覆盖课程交付所需材料，不是只写一份泛泛的项目介绍。

### 3.2 需求边界写得具体

`需求报告-V5.0.md` 和 CG04 都能明确列出“本期做”和“本期不做”，并解释为什么不把对话式报修、工资绩效、多校区、仓库进销存等混入主线。这种写法能有效防止项目范围膨胀，也方便答辩时说明取舍。

### 3.3 有较强的可验收意识

文档不是只写“系统稳定、操作方便”，而是大量采用可判断语句，例如：

- 非法状态返回 409，越权返回 403，前置条件不满足返回 422。
- 被拒绝后状态和版本不变。
- AI 不可用时仍能建单并记录 `FALLBACK`。
- 配件到货后，超预算事实仍保留到归档。
- 返修必须先经管理员审查，旧旁路不得生成返修单。

这类表述比泛泛而谈更专业，也是整套文档最值得保留的部分。

### 3.4 对系统边界和未完成项较诚实

`06_再次改进计划/README.md` 和生产试点执行记录明确区分“本地预验收”和“生产准入”，没有直接宣称生产就绪。根 README 也列出了真实 S3、目标环境、真实试点等待完成事项。这种边界意识很好，应同步到所有 CG 文档，而不是只保留在最新改进记录里。

### 3.5 变更记录具有可追溯性

返修审查、管理员撤销、幂等、AI 审计、文件治理等改进均有执行记录，能说明改了什么、如何验证、还缺什么。相比只写最终结论，这种材料更能体现软件工程过程。

### 3.6 表达总体清楚，视觉材料易读

表格、错误码、工单号、接口路径和示例描述比较具体。CG12 海报层级清楚、重点数字醒目，视觉表达没有明显问题；主要问题是其中的数字和结论已经过期，而不是版式本身。

## 四、必须优先解决的问题

## P0：不修改就会影响提交、演示或事实可信度

### P0-1　CG08 源代码包与当前项目不一致

**证据：**

- 当前 CG08 生成于 2026-11-18，只有 365 个条目。
- 包内没有 `app/student-web`、`app/worker-web`、`app/admin-web`，也没有 `docs/06_再次改进计划`。
- 包内 `TransitionTable.java`、`schema.sql`、`README.md` 与当前文件大小和内容版本均不同。

**影响：** 交付文档描述的是当前系统，但源代码包仍是旧系统，属于实质性交付不一致。即使其他文档全部改好，也不能直接提交这个 ZIP。

**处理：** 在全部代码和文档冻结后重新生成 CG08，并至少核对三端目录、最新后端、AI、迁移脚本、测试脚本和当前文档是否入包。

### P0-2　状态机、管理员撤销和返修触发方存在多版本冲突

**当前实现：** 14 条合法转移，新增 `REPAIRING + ADMIN_CANCEL → CANCELLED`；管理员批准维修中撤销已经是正式业务接口，不再返回 501。返修由学生申请、管理员审查，批准后由管理员触发 `REJECT`。

**仍在使用旧说法的材料：**

- `需求报告-V5.0.md`、`V5.0-统一说明.md`：仍写 13 条转移。
- `工单状态机图-V5.0.html/.png`：仍写 13 条，并在图中将 `REJECT` 标为学生直接触发。
- CG02：CR-001 仍写“未批准、接口 501”。
- CG04：仍写 13 条，G-02 仍写未实现。
- CG09、CG10：仍把 501 当作预期结果和演示点。
- `答辩演示脚本.md`：仍要求现场演示 501，并解释该边尚未批准。
- CG11 生成源、CG12 海报：仍使用 13 条、130 格等旧数字。
- `SYS-005_系统设计说明书.md`：前文写 14 条，第十章又写“9 状态 / 13 转移”。

**影响：** 评阅者会看到互相矛盾的核心业务规则；按答辩脚本操作还会得到与讲稿不同的结果，直接影响现场可信度。

**处理：** 以当前实现为基线，统一修改全部受控文档、图、CG 生成源和答辩话术；旧 13 条版本只保留在明确标记的历史记录中。

### P0-3　用户手册和答辩脚本已不能指导当前系统运行

**典型问题：**

- CG10 仍写单个 Vue 前端 5173，当前正式入口为学生 5173、师傅 5174、管理端 5175。
- CG10 仍写“演示版不做真登录、请求头切换身份”，当前已有 Bearer Token、会话撤销和重启恢复。
- CG10 仍写样本 `seeded=7`，当前根 README 为 11 张样本单。
- CG10 仍写批准撤销返回 501，与当前实现相反。
- `答辩演示脚本.md` 仍使用 `node app/server/index.js`、SQLite 和旧 Node 测试命令；当前正式后端是 Spring Boot + MySQL。
- 答辩脚本仍写“真实并发没压测、AI 是词表规则不联网、照片是占位串”，这些均已不能准确描述当前本地预验收版本。

**影响：** 文档无法作为用户手册使用，答辩时容易启动错误项目或讲出过时结论。

**处理：** CG10 和答辩脚本应优先于一般文字润色进行重写，并用当前系统实际跑一遍完整演示流程。

## 五、重要一致性与内容问题

## P1：应在正式提交前全部修正

### P1-1　正式 CG 文档整体落后于最新实现

多份 CG 文档仍停留在“单一 `app/web`、15 张表、请求头身份、规则 AI、占位照片、撤销未开放”的旧阶段，而当前材料已经记录：

- 学生、师傅、管理端三个独立 Vue 应用。
- Bearer Token 鉴权和持久化会话。
- 真实上传、私有文件读取和本地文件治理；真实 S3 仍待部署。
- 真实模型接入、AI 审计、规则兜底和失败降级。
- 管理员撤销、幂等、旧返修旁路关闭。
- 本地预验收和本地压力测试已经完成，但目标环境试点未完成。

**建议：** 不要用“新增一段最新进展”的方式补丁式处理，应重新生成整套 CG，保证同一份文档内部也没有前后冲突。

### P1-2　测试数字、矩阵数字和算术口径混乱

| 材料 | 当前写法 | 问题 |
|---|---|---|
| CG09 | 34 JUnit、22 pytest、130 格、13 合法、117 非法 | 已过期 |
| 根 README | 111 JUnit、29 pytest | 与当前已有报告和本次实测不一致 |
| `docs/README.md` | CG09 仍标为 34 JUnit + 22 pytest | 索引同步失效 |
| `app/server/README.md` | `10 × 13 = 140` | 算术错误，应为 `10 × 14 = 140` |
| `StateMachineTest.java` 注释/显示名 | 117、96 等旧数字 | 测试能运行，但说明文字会误导审查者 |
| CG11/CG12 | 13 条、130 格、34 项、22 条 | 演示材料仍是旧口径 |

**推荐统一口径：**

- 全矩阵：10 行 × 14 事件 = 140 格，14 格合法，其余 126 格不合法。
- 如果只讨论“9 个已有状态 × 13 个会改状态的事件”这一单测子集，非法组合为 104；它与全矩阵 126 不是同一统计范围，不应混写。
- Java 测试数量以当次实际 Surefire 汇总为准；当前已有报告为 130 tests、0 failures、0 errors、2 skipped。
- AI 当前实测为 31 passed；前端旧共享包为 8 passed；原型为 34 通过。

**额外建议：** 测试报告不要只写一个不断变化的“最新总数”，应附测试日期、代码基线、执行命令和原始报告位置，避免每次新增用例后全站手工改数字。

### P1-3　数据库表数未区分统计场景

文档中同时存在 15、16、20、21 张表等说法。它们有些来自不同历史阶段，有些来自不同统计方式，但现在没有统一说明。

**建议固定写法：**

- 当前 `schema.sql`：20 张业务表，另有 `v_user_account` 兼容视图。
- 完整运行库：20 张业务表 + `t_schema_migration` = 21 张表，另有 1 个兼容视图。
- 旧库迁移期如有额外遗留表，应单独列出，不与新库数量混用。

同时更新 CG04、CG05、CG06、SYS-005、系统开发设计 README、开发计划 README 和 docs 总索引。

### P1-4　同一需求报告的 Markdown 与 Word/PDF 内容不同

`docs/README.md` 已说明 Markdown 是返修审查修订稿，Word/PDF 是 V5.0 原稿，但这些文件仍同时放在生效需求目录中：

- Markdown 已写“学生申请、管理员审查后生成返修单”。
- Word 原稿仍写“学生验收不通过直接生成返修单”，并将 `REJECT` 触发方写为学生。

**影响：** 即使索引写了优先级，评阅者直接打开 Word/PDF 仍会读到旧业务规则。

**处理：** 用修订后的内容重新导出 Word/PDF；若必须保留原稿，应移到 `99_存档` 并在文件名中明确“旧版”。

### P1-5　“零人工完成率”定义在逻辑上自相矛盾

需求报告一处把严格口径定义为“全部事件均为系统产生”，同时又说学生提交和师傅打卡也算人工，最后却解释该指标“严格指没有管理员介入”。这三句话不能同时成立：正常工单一定有学生和师傅的人工事件，严格口径几乎必然为 0。

**建议：**

- 主指标改名为 **“无管理员介入完成率”**，定义为完成工单中无管理员推进/审批事件的占比。
- 若确实需要“全自动事件率”，另列为诊断指标，不与主闭环目标混用。
- 在指标名称、公式、事件范围、统计分母、返修链聚合方式上保持一致。

### P1-6　部分目标声称可量化，实际没有目标值或统计口径

“零人工完成率高”“返修率低”“管理端大部分时间是空的”被称为量化判据，但文档没有给出目标阈值、样本量、统计周期或试点基线。NFR 也存在响应时间多套写法，例如建单 2 秒/3 秒、P95 300ms、AI 3 秒/1500ms，需要区分本地与目标环境、快速分类与异步复核。

**建议：** 不要凭空补一个漂亮数字。可以先写“课程演示验收口径”和“试点目标待基线测量后确认”，并明确样本量、统计周期、P95/P99 和环境。

### P1-7　团队、工期和提交基线说法不一致

- CG02/CG03 以 5 人团队、5 人×12 周、四个月为口径。
- 开发计划 README 明确写“基本由同一开发者推进、18 个工作日单人顺序执行”。
- CG02 写本地 `master` 单线、8 次提交；最新改进总纲写已推送 GitHub 最新 `main`。
- CG05–CG07 仍以 `9a537dc` 为代码基线，已经不能覆盖后续大量改进。

**处理：** 按实际情况统一团队人数、分工、工期、仓库分支和代码基线。若确实是一人主开发，不应为了显得完整而虚构五人协作过程；可写“角色视角”而不是虚构成员产出。

### P1-8　CG03 可行性研究需要更新证据和成本口径

CG03 的结构不错，但目前存在三类问题：

1. “需求真实”的论证主要是四个可观察现象，没有访谈人数、样本量、记录日期或基线数据，证据强度有限。
2. 技术部分仍写“规则引擎而非大模型、不依赖外部 API、外部依赖 0 元”，与当前真实模型接入不一致。
3. 成本只覆盖本地演示，未区分模型 API、对象存储、HTTPS、监控等生产试点成本。

**建议：** 将结论拆成“课程演示可行性”和“生产试点可行性”。没有真实调研数据时，写“待访谈/待试点验证”，不要把推测写成已证实事实。

### P1-9　交付状态和占位信息尚未收口

- 多份文档仍有“示范大学”“待填学号姓名”“第 X 组”“指导教师待填”等占位。
- CG01 已把多数交付物标为“已交”，但 CG08 明显过期、CG13 仍是模板，状态用词不准确。
- CG14 已预填五人分数，但成员姓名、学号仍为空；需要确认这些分数是示例还是正式评价。
- CG13 仍是骨架，不应被当作已完成的个人体会提交。

**建议：** CG01 状态改为“已生成 / 待补信息 / 待复核 / 可提交”等内部状态，只有实际提交后才写“已交”。

## 六、文档治理方面的根本问题

### 6.1 “单一事实源”写了，但没有执行到底

项目多次声明“状态机只有一个真相”“接口只认契约”“冲突时按优先级取”，但当前实际情况是：

- docs 索引写 14，链接正文写 13。
- SYS-005 同一文档前文写 14，后文写 13。
- SYS-003 头部上游依据写 13，正文又写 14，事件表还没有完整纳入 `ADMIN_CANCEL`。
- CG 由脚本生成，但生成源本身仍是旧内容，所以“自动生成”只是在稳定复制旧错误。

**根因：** 没有一个发布前必须完成的“基线冻结—全量替换—重生成—一致性检查”闭环。

### 6.2 历史记录和当前有效文档混杂

`old` 目录保留旧计划没有问题，执行记录保留历史测试数字也没有问题；问题在于需求、图、用户手册、答辩脚本和 CG 这些“当前生效材料”也保留了旧口径。

**建议：** 历史数字可以留在执行记录中，但必须带日期和基线；当前文档只保留当前口径。不要为了消除历史记录而改写过去，也不要让历史记录进入当前操作指南。

### 6.3 版本号和状态标签没有及时升级

多份文档版本仍写 V1.0/V1.2，但内容经历的状态机、数据库、鉴权、文件和 AI 变化已经足以形成新版本。部分文档同时写“已实现并验收”和“待评审”，状态含义不清。

**建议统一状态词：**

- 草稿：内容仍在编写。
- 待评审：内容完整，但尚未确认。
- 已实现并本地验证：代码和本地测试完成。
- 目标环境待验收：不能写成生产就绪。
- 已归档：仅供历史追溯。

## 八、文字与结构上的进一步优化

这些不是最紧急的问题，但完成 P0/P1 后可以明显提升专业感。

### 8.1 减少口号式句子重复

“让它自己跑”“管理端大部分时间是空的”“写成一个不让它出错的形状”等句子适合答辩标题，但在需求、设计、构造、测试和可行性报告中反复出现，会显得宣传化。建议：

- 标题和答辩中保留少量有记忆点的表达。
- 正式规格说明书中改为客观、可验证的句子。
- 每份文档突出自己的职责，减少跨文档整段重复。

### 8.2 将“已实现”“已验证”“可上线”严格分开

建议全站统一以下表述：

- 代码存在：已实现。
- 自动化测试通过：已本地验证。
- 本地一键验收通过：本地预验收通过。
- 目标环境部署完成：已部署到指定环境。
- 真实用户试点和业务签字完成：才讨论正式验收或生产准入。

### 8.3 为证据增加定位信息

测试报告和可行性报告中的关键结论，建议附上：日期、代码提交、命令、原始日志/截图位置、执行环境。这样比只写“全部通过”更可信，也能避免后续无法判断数字属于哪个版本。

### 8.4 正式 Word 文档更新实际目录和页码

提取文本中仍有“可在 Word 里用引用→目录自动生成”的提示语。正式导出前应生成真正的自动目录、页码和图表编号，并检查分页、表格跨页、字体和页脚，不要把操作提示留在成稿里。

### 8.5 修正文档索引中的目录说明

`docs/README.md` 的目录树仍主要描述 01–04 和 99，未完整反映 05、06、07 等现有目录。建议补充当前文档地图，并注明 07 为独立审查材料，不参与业务口径裁决。

## 十二、最终结论

这套项目文档的优点很明确：**材料齐、思路清楚、工程意识较强、敢于写边界和失败路径**。目前最大的问题不是措辞，而是**文档版本没有跟上系统演进**，并且已经影响源代码包、用户手册、测试报告、状态机图和答辩材料的一致性。
