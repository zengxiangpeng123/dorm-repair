## 二、每条为什么这么定

1. **学生只多填一个选填框，不多一道手续。** 「什么时候寝室有人」是大纲里本来就有的，它是「到访未遇」的事前解法：能约掉就不必靠事后顺延。做成必填会挡住急着报修的人，所以选填 + 默认全天。
2. **一条混合权重在代码里只有一个能生效。** 「安全等级 → 楼栋合并 → 等待时长」写成比较器时，第一个键不等就不会看第二个，等于后两个白写。拆成四层后每层职责单一：安全闸管「要不要插队」，截止时间管「先做谁」，紧急度管「同时到期的先做谁」，先来先修防饿死。
3. **楼栋不该是排序键。** 楼栋是「攒批」的分组维度——同楼栋、时段重叠的单合成一个批次给同一个师傅；一旦把它塞进排序键，就会为了凑批把一单压后，出现「同一栋的单越攒越晚」。
4. **两个 7 天合成一个，必然出 bug。** 起点不同（交完工照 vs 学生签字）、终点不同（已完成 vs 已关闭）。合在一起只有两种结果：刚签完字就被归档，或者永远不归档。
5. **例外的正确位置是「边」，不是「点」。** 三类例外都挂在某条转移上（提交、登记缺件、第二次验收不通过），发生后工单该怎么走还怎么走。给它们开状态位，等于让工单停下来等人——那就又长出一个审批岗。

## 三、状态机对齐结果

大纲里出现过的状态一个不少；大纲没写的**已取消**按系统已实现口径补上（撤销只到「师傅进楼打卡」之前，进楼后只能申请）。

- **9 个状态**：待派工 / 已派工 / 维修中 / 待配件 / 待验收 / 返修中 / 已完成 / 已关闭 / 已取消
- **14 条合法转移**：事件命名与 `SYS-004《状态机设计》` 一致（SUBMIT / ASSIGN / ARRIVE / NO_SHOW / FINISH / NEED_PARTS / PARTS_ARRIVED / ACCEPT / REJECT / AUTO_ACCEPT / ARCHIVE / CANCEL×2 / ADMIN_CANCEL）
- **三条回流全部回「待派工」**：到访未遇、配件到货、返修新单。没有一条直接回「维修中」——否则师傅会凭空多出一张没推送过的单

## 五、还没定的一件事

**可上门时段的粒度。** 大纲只写「具体什么时间寝室有人」，没说是一天三段（上午/下午/晚上）、两小时窗口，还是让学生自由填。现在的图按「默认全天、可选时段」画，粒度不影响流程形状，但影响两件事：批次能不能凑上、截止时间怎么算。定粒度时需要一起定这两条。
