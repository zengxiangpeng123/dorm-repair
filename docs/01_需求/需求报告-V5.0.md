## 一、项目概述

### 1.1 现在的问题

宿舍报修目前散在三个地方：电话、微信群、宿管登记本。一件事被拆成三段口口相传，带出四个后果：

- 入口不统一。同一处设施被反复报，也有人报了一次就再没人管；事后没法统计到底报过几次。
- 进度不可见。学生只知道「说了」，不知道单子在谁手上、到哪一步，只能反复问宿管。
- 派单靠人记。宿管凭印象判断谁在、谁离得近，师傅手上的活轻重不均，急的活可能排在后面。
- 修完没记录。出了返修查不到上次是谁、什么时候、换了什么件，同一个点反复坏也发现不了。

### 1.2 目标

把报修收进一个入口，让它沿一条固定主线自己走完：学生手机上报修 → 系统自动受理并定级 → 自动派给该楼栋师傅 → 师傅到门打卡、维修、交完工照 → 学生验收签字 → 系统归档。主流程不需要任何人点头；管理端不参与正常推进，只在返修审查、维修中撤销审批和四类例外上介入。

课程演示使用以下可执行判据；业务成效阈值须在真实试点取得基线后确定，不把“高/低”当成已测量结论：

- 不用人点头，工单也能从提交走到关闭；
- 管理端看板大部分时间是空的，管理员不靠盯单子干活；
- 无管理员介入完成率与返修率均有明确定义、样本范围和统计周期；真实目标阈值待试点基线确认。

### 1.3 范围

| 分类 | 内容 |
| --- | --- |
| 本期做 | 报修 → 受理 → 派工 → 维修 → 验收 → 归档 的闭环；AI 故障定级与排队排序；两个自动计时器（验收超时、归档）；管理端看板、例外清单与住宿台账；闭环回流（高频点位提前换件、AI 规则校准）。 |
| 本期不做 | AI 对话式报修（大纲中已标注「当前版本不做」）；多校区、多学校共用一套；师傅绩效与工资核算；语音报修、视频报修；维修物料仓库的进销存。 |
| 为什么这样切 | 闭环先转起来，才谈得上优化。对话式报修只是把「填表」换成「说话」，不改变任何一条流转规则，可以后补；绩效与仓库是另一个系统的事，混进来会把主线拖长。 |

## 二、角色与权限

系统里只有四种身份：学生、维修师傅、管理员、系统。一个账号一个角色，登录后按角色自动进对应端，不需要选。四类人看的是同一张单的不同面，不是四套数据。

| 角色 | 是谁 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| 学生 | 住在这栋楼的人 | 提交报修；看自己单子的实时进度；验收签字或申请返修；在师傅进楼前撤销 | 看不到别人的单；不能自己定紧急程度；不能改已提交的内容 |
| 维修师傅 | 归属某个楼栋的维修工 | 看待办（一单一张卡）；到门打卡；报「进不了场」或「缺配件」；交完工照 | 不能接非本楼栋的单；不能替别人打卡；不能自己把单子标成完成 |
| 管理员 | 宿管／后勤主管 | 看看板；审查返修申请；处理三类例外；审批维修中撤销；维护住宿台账与预算线；事后抽查 | 不参与正常工单推进；除返修审查和撤销审批外不能改在办工单状态；不能替学生签字 |
| 系统 | 后台程序 | 自动受理、AI 定级、排队派工、超时自动验收、到期归档、规则校准 | 不做需要人判断的决定；不静默吞掉异常 |

*表 2-1　角色与权限*

权限的一条硬约束：越权操作一律返回错误码，不静默忽略。非本单师傅执行「到门打卡」「完工提交」，非学生本人执行「验收通过」，非授权管理员执行「返修审查」，都必须被拒绝——静默忽略会让时间线出现假的空档。

## 三、功能需求

八项功能对应闭环的八段，编号 FR-01 ~ FR-08。每项给出输入、规则与验收标准，验收标准写成可执行的判断，不写「体验良好」这类无法验证的话。

### FR-01　登录与角色分流

**输入：**手机号 + 验证码，或学号／工号 + 密码。

**规则：**账号绑定唯一角色；登录成功后按角色直接进学生端／师傅端／管理端，不出现「请选择身份」；同一账号在两端同时登录时，后登录者挤掉前者。

**验收：**学生登录后首个页面是「我的报修」，不是首页；管理员登录后先看到看板，返修审查与例外清单在管理端队列中处理。

### FR-02　学生提交报修

**输入：**现场照片（必填，至少 1 张）、问题描述（必填，至少 4 个字）、可上门时段（选填）；楼栋、寝室号、手机号由账号自动带出。

**规则：**紧急程度不由学生选，由系统按 AI 判断给出；提交成功立即返回工单号（形如 BX20261117001）；同楼栋的单自动归入同一批次；描述不足 4 字或没有照片时提交按钮不可用，并说明缺什么。

**验收：**不填可上门时段也能提交成功，工单按「全天可上门」参与排序；连续提交两单不会产生重复工单号。

### FR-03　系统自动受理

**输入：**新工单（含照片、描述、楼栋、时段）。

**规则：**AI 判故障类型（给排水／电气／电器／门窗家具／网络）与紧急程度（紧急／较急／普通）；命中安全类（漏电、漏气、水管爆裂等）直接定「紧急」；置信度低时保守升一档，照样放行，不停单等人；按四层规则入队（见 4.2）；派给该楼栋当班师傅。

**验收：**AI 判断结果与依据写入工单，学生和师傅都能看到；AI 服务超时或报错时，工单降级为「普通」照常入队，不允许因为 AI 不可用而丢单。

### FR-04　维修端作业

**输入：**今日待办列表（一单一张卡：寝室号、可上门时段、故障摘要、一键导航）。

**规则：**到门打卡即记录到场时间并同步给学生；打卡后依次判断「能进场吗」与「能当场修好吗」：进不了场填原因，系统顺延重排；缺配件时填名称、金额、预计到货日期，预算内自动下单，超预算转管理端；能当场修好则修完上传完工照（至少 1 张）并提交。

**验收：**师傅端整屏只有三个可点按钮（打卡／报异常／交完工），其余只读，全程不需要打字（异常原因从固定选项里选）；完工照未上传时提交被拦下并提示。

### FR-05　学生验收

**输入：**完工照、维修说明、工单历史。

**规则：**验收通过 → 电子签字 → 工单完成；验收不通过 → 必须填原因并提交返修申请，不直接生成返修单；管理员确认属于维修质量问题后，原单转「返修中」并生成 -R1（如 BX20261117001-R1），继承原单的位置、照片与历史，紧急度升一档；确认误报则驳回申请，原单按正常验收、归档流程继续处理；每次返修都要审查，第 2 次起同时标记「反复返修」；待验收超过 168 小时无响应，系统自动确认完成并标注「学生 7 天未响应」。

**验收：**签字后工单立即变「已完成」且不可再改；返修申请经管理员确认后才生成独立新单，原单保留全部历史并挂起，不覆盖、不删除；误报则驳回申请，不生成返修单。

### FR-06　系统归档

**输入：**已完成工单。

**规则：**学生签字满 7 天后自动归档：工单转只读，打包提交照、AI 判断依据、到访记录、完工照、电子签字与全链路时间戳，同时并入看板统计。

**验收：**归档后的工单任何角色都不能修改；归档记录可追溯到每一次状态变化的时间与操作人。

### FR-07　管理端审查与监测

**输入：**看板、返修审查队列与例外清单。

**规则：**看板展示：在办工单分布、平均修复时长、返修率、无管理员介入完成率。例外清单只露三类：数据对不上（学生填的位置与住宿台账不一致）、超预算采购、同一单反复返修。除返修审查和维修中撤销审批外，事后抽查只读，不改在办工单。另维护住宿台账，供系统核对位置。

**验收：**三类例外发生时，工单状态不发生任何变化，只在清单里多一条记录；返修审查与维修中撤销审批按各自流程处理，不占例外名额。

### FR-08　闭环回流

**输入：**归档数据、例外处理结论。

**规则：**归档数据回流看板，识别高频点位并安排提前换件；例外处理结论回流 AI 规则，调整故障分类与紧急度判断阈值，改完回到自动受理环节生效。

**验收：**一次规则调整不需要改代码、不需要停机；调整前后同一批历史工单的重判结果可对比。

## 四、业务规则

### 4.1 AI 故障定级

两级判断：先判故障类型，再判紧急程度。故障类型固定五类——给排水、电气、电器、门窗家具、网络；紧急程度固定三档——紧急、较急、普通。

- 安全类优先。描述或照片命中安全关键词（漏电、跳闸冒烟、漏气、水管爆裂、门窗脱落等），不看置信度，直接定「紧急」。
- 置信度低就升一档。分类置信度低于阈值时，紧急程度保守上调一档（普通→较急，较急→紧急），并且照常放行。理由是：猜错的代价——多派一次工——远小于压着不动的代价。
- 定级依据必须留痕。判断结果、命中的关键词、置信度一起写进工单，学生和师傅都能看到为什么这么判；这也是后续规则校准的素材。
- AI 不可用不拦单。调用超时或报错时按「普通」入队，工单照走，异常记入日志。

### 4.2 排单：四层排序

排序规则拆成四层，逐层生效，前一层分出胜负就不看后面：

| 层 | 键 | 作用 | 为什么是这一层 |
| --- | --- | --- | --- |
| ① | 安全闸 | 命中安全类的单直接派工，不参与排队 | 安全问题的等待成本最高，不能和人比先后 |
| ② | 截止时间 | 可上门时段 + 已等待时长，越紧迫越靠前 | 「什么时候寝室有人」决定了能不能上门，错过就要再等一天 |
| ③ | 紧急度 | 较急 > 普通（紧急已被①提走） | 同样到期时，影响面大的先做 |
| ④ | 先来先修 | 提交时间早的先做 | 兜底，防止低优先级单被无限期压后 |

*表 4-1　四层排序*

楼栋不参与排序，只用于攒批：同一楼栋、可上门时段重叠的单合成一个批次交给同一个师傅，一次上门处理多单。把楼栋塞进排序键会出问题——为了凑批把某一单往后压，就会出现「同一栋的单越攒越晚」，而且一旦第一个键不等，后面的键根本不生效。

### 4.3 预算线

配件采购设一条单次预算线（具体金额由后勤按年度核定，系统中为可配置项）。金额在预算线内，系统自动下单，师傅等件，工单停在「待配件」；超出预算线，进例外清单等管理员点头，但工单状态不变——它已经在「待配件」了，批准与否只改采购状态。

### 4.4 返修

学生验收不通过时，先提交返修申请，不直接生成返修单。原单继续停在「待验收」，保留全部历史（照片、到访记录、每次判断依据），并进入管理端审查。管理员确认属于维修质量问题的，原单才转入「返修中」，并生成返修单：单号为原单号加 -R1（后续依次为 -R2、-R3），新单指向原单，继承位置、照片与历史，紧急度升一档后重新排队。确认属于学生误报或并非维修质量问题的，驳回申请，不生成返修单，原单按正常验收、归档流程继续处理。每次返修都必须先经管理员审查；第 2 次及以后同时标记为「反复返修」例外，由管理员判断是手艺问题还是设施本身该更换。

### 4.5 两个计时器

「7 天」在系统里出现两次，指的是两件不同的事，起点和终点都不同，不能合成一个：

| 编号 | 名字 | 起点 | 时长 | 终点 | 防的是什么 |
| --- | --- | --- | --- | --- | --- |
| T1 | 验收超时 | 师傅提交完工照 | 168 小时 | 已完成（自动确认） | 学生不验收，单子永远吊着，师傅的活算不算干完说不清 |
| T2 | 归档 | 学生签字（含自动确认） | 7 天 | 已关闭（只读） | 单子停在已完成不归档，统计口径一直飘 |

*表 4-2　两个「7 天」*

合成一个计时器只会出两种错误：刚签完字就被归档，或者永远不归档。

### 4.6 撤销边界

学生能撤销到哪一步，划线的依据不是技术限制，是成本：

| 工单状态 | 学生能做什么 | 为什么 |
| --- | --- | --- |
| 待派工 | 直接撤销 | 还没人动，零成本 |
| 已派工（未打卡） | 直接撤销 | 师傅还没出发，只需从待办里去掉 |
| 维修中（已进楼） | 只能申请，由管理员决定作废或补偿师傅 | 师傅已经跑了一趟，撤销要先确认 |
| 待验收及以后 | 不能撤销 | 活已经干完了 |

*表 4-3　撤销边界*

分界线就是「进楼打卡」：打卡前师傅还没出发，打卡后人已经在楼里。维修中的撤销申请和返修审查，是全系统由管理员决定、能够改变工单状态的两处入口；其余例外只产生标记和清单条目。

## 五、工单状态机

一张单只能停在这九个位置之一，靠固定事件挪动，没有「看情况」的分支。状态与事件命名与 SYS-004《状态机设计》一致。

### 5.1 状态定义

| 状态 | 代码值 | 含义 | 终态 |
| --- | --- | --- | --- |
| 待派工 | PENDING | 已入库，等批次凑齐 | 否 |
| 已派工 | ASSIGNED | 已推给某个师傅 | 否 |
| 维修中 | REPAIRING | 师傅已到门打卡 | 否 |
| 待配件 | PARTS | 缺件等待采购 | 否 |
| 待验收 | VERIFYING | 完工照已提交 | 否 |
| 返修中 | REWORKING | 管理员批准返修申请，原单挂起 | 否 |
| 已完成 | DONE | 学生已签字 | 否 |
| 已关闭 | CLOSED | 已归档，只读 | 是 |
| 已取消 | CANCELLED | 学生撤销，工单作废 | 是 |

### 5.3 必须被拒绝的转移

以下操作一律返回 409（状态冲突），不是静默忽略——静默忽略会让调用方以为成功，时间线上留下假的空档。

| 非法操作 | 为什么禁止 |
| --- | --- |
| 待派工 → 维修中 | 跳过派工，师傅没有依据 |
| 待派工 → 已完成 | 跳过整个维修过程 |
| 已派工 → 待验收 | 没打卡就到完工，时间线断了 |
| 维修中 → 已完成 | 跳过学生验收 |
| 待配件 → 已完成 | 缺件没换上就结单 |
| 待验收 → 待派工 | 只能经管理员批准生成返修单，不能凭空回队 |
| 维修中 → 已取消 | 师傅已进楼，学生只能申请，由管理员决定 |
| 待验收 → 已取消 | 已完工，只能验收或退回返修 |
| 已关闭 / 已取消 → 任意 | 终态不可逆；需要就重新报修 |
| 非本单师傅执行 ARRIVE / FINISH | 越权 |
| 学生执行非本人 ACCEPT / 非管理员执行 REJECT | 越权 |

### 5.4 实现约束

- 表驱动。状态转移写成「当前状态 + 事件 → 目标状态」的映射表，统一由状态机计算目标状态；不允许在业务代码里直接改状态字段。
- 乐观锁。更新状态时带上版本号，受影响行数为 0 说明别人已经改过，返回 409「状态已变化，请刷新」，只允许一个请求成功。
- 统一写时间线。每次转移都追加一条事件记录（事件、操作人、是否人工、时间），并更新工单的状态时间。
- 位置校验。建单和管理员创建人员时，楼栋必须存在；楼栋不存在时分别返回 `422 BUILDING_NOT_FOUND` 和 `400 BAD_REQUEST`，不得生成不可派工、不可看板的数据。
- 人工标记。操作人类型为系统时标为 0，学生／师傅／管理员标为 1。无管理员介入完成率 = 没有 ADMIN 角色事件的已完成/已关闭工单 ÷ 已完成/已关闭工单总数。学生提交、验收和师傅到场、完工是必要人工动作，不扣减；另保留全部事件 manual=0 的事件级诊断，不把结构性恒 0 的值当主指标。
- 回流不新增状态。到访未遇、配件到货都回到「待派工」，不单开状态；反复未遇靠事件条数统计，不需要额外字段。

## 七、验收标准

### 7.1 闭环判据

三条同时成立，才算这套系统真的把闭环转起来了：

- 无管理员介入完成率：已完成/已关闭工单中没有 ADMIN 角色事件的占比；课程演示记录分子、分母与统计时间，目标阈值待试点确认；
- 返修率低：同一单返修 2 次及以上的比例低于设定目标；
- 管理端是空的：看板与例外清单长期处于「没什么可处理」的状态——管理端忙，说明流程在设计上还没走通。
