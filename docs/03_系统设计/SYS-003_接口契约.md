## 一、通用约定

### 1.1 基础

| 项 | 约定 |
|---|---|
| 基础路径 | `/api/v1` |
| 传输 | JSON，`Content-Type: application/json`（上传除外） |
| 编码 | UTF-8 |
| 时间格式 | `yyyy-MM-dd HH:mm:ss`，服务端时区固定 `Asia/Shanghai`；客户端不传时间，一律服务端生成 |
| 工单号 | `BX` + 8 位日期 + 3 位当日序号 = `BX20261117001`；返修单在原单后加 `-R1`、`-R2` |
| 版本控制 | 每个工单带 `version`（整数），每次转移 +1 |

### 1.2 鉴权与角色

```
Authorization: Bearer <token>
```

四种角色，**一个账号一个角色**：

| 角色 | `role` 值 | 能发的事件 |
|---|---|---|
| 学生 | `student` | `SUBMIT` `ACCEPT` `CANCEL` `REWORK_REQUEST` |
| 维修师傅 | `worker` | `ARRIVE` `NO_SHOW` `FINISH` `NEED_PARTS` |
| 管理员 | `admin` | `REJECT` `REWORK_REJECTED` `PARTS_ARRIVED`（+ 待变更的 `ADMIN_CANCEL`） |
| 系统 | `system` | `ASSIGN` `PARTS_ARRIVED` `AUTO_ACCEPT` `ARCHIVE` |

系统身份用于内部定时任务与派工引擎，用服务间密钥鉴权，**不对客户端开放**。

### 1.3 统一响应体

成功：

```json
{ "ok": true, "data": { } }
```

失败：

```json
{
  "ok": false,
  "error": {
    "code": 409,
    "message": "状态「待派工」不接受事件「完工提交」",
    "from": "PENDING",
    "event": "FINISH",
    "allowed": ["ASSIGN", "CANCEL"]
  }
}
```

`from` / `event` / `allowed` 三个字段**只在 409（状态冲突）时出现**。这是硬要求：前端要能据此把"当前能做什么"画出来，测试也要靠它断言。

### 1.4 错误码

| HTTP | 语义 | 什么时候用 | 前端怎么办 |
|---|---|---|---|
| 400 | 参数格式错 | JSON 解析失败、字段类型不对 | 提示，不重试 |
| 401 | 未登录 / token 失效 | — | 跳登录 |
| 403 | 越权 | 非本单师傅打卡、非本人验收、学生调系统接口 | 提示"无权操作" |
| 404 | 工单不存在 | 单号查不到 | 提示 + 回列表 |
| **409** | **状态冲突** | 非法转移、乐观锁冲突 | 刷新详情，重画按钮 |
| 422 | 业务规则不满足 | 照片 0 张、描述 < 4 字、缺件字段不全、未遇原因为空 | 就地提示，改完可重试 |
| 500 | 服务端错 | — | 提示"稍后再试" |
| 501 | 功能未开放 | `ADMIN_CANCEL` 未过变更单 | 隐藏入口 |

**409 与 422 的分界线**：状态机里没有这条边 → 409；有这条边但前置条件不满足 → 422。

### 1.5 乐观锁

写接口在请求体里带上客户端看到的 `version`：

```json
{ "version": 3, "event": "..." }
```

- `version` 与服务端不一致 → `409`，`message` 为「状态已变化，请刷新」，`error.reason = "VERSION_CONFLICT"`。
- `version` 缺省时不校验（仅限演示环境；生产必须传）。

### 1.6 幂等（可选，P1）

写接口支持 `Idempotency-Key: <uuid>`。同一 key 重复提交返回首次结果，不再执行转移。用于防止师傅连点两下打卡。

### 1.7 分页

```
?page=1&pageSize=20
```

响应附带 `{ "page": 1, "pageSize": 20, "total": 57 }`。列表默认按 `createdAt` 倒序，队列类接口按排队规则正序。

## 二、状态与事件对照

### 2.1 九个状态

| 状态 | 代码值 | 终态 |
|---|---|---|
| 待派工 | `PENDING` | 否 |
| 已派工 | `ASSIGNED` | 否 |
| 维修中 | `REPAIRING` | 否 |
| 待配件 | `PARTS` | 否 |
| 待验收 | `VERIFYING` | 否 |
| 返修中 | `REWORKING` | 否 |
| 已完成 | `DONE` | 否 |
| 已关闭 | `CLOSED` | **是** |
| 已取消 | `CANCELLED` | **是** |

### 2.2 十二个事件 → 十二条命令

13 条转移对应 **12 个事件**（`CANCEL` 有两个来源状态，共用一条命令）。

| # | 事件 | 命令 | 触发方 | 从 → 到 |
|---|---|---|---|---|
| 1 | `SUBMIT` | 建单 | 学生 | — → `PENDING` |
| 2 | `ASSIGN` | 派工 | 系统 | `PENDING` → `ASSIGNED` |
| 3 | `ARRIVE` | 打卡 | 师傅 | `ASSIGNED` → `REPAIRING` |
| 4 | `NO_SHOW` | 报未遇 | 师傅 | `ASSIGNED` → `PENDING` |
| 5 | `FINISH` | 完工 | 师傅 | `REPAIRING` → `VERIFYING` |
| 6 | `NEED_PARTS` | 报缺件 | 师傅 | `REPAIRING` → `PARTS` |
| 7 | `PARTS_ARRIVED` | 配件到货 | 系统 / 管理员 | `PARTS` → `PENDING` |
| 8 | `ACCEPT` | 验收通过 | 学生 | `VERIFYING` → `DONE` |
| 9 | `REJECT` | 审查通过，进入返修 | 管理员 | `VERIFYING` → `REWORKING` |
| 10 | `AUTO_ACCEPT` | 超时自动验收 | 系统 | `VERIFYING` → `DONE` |
| 11 | `ARCHIVE` | 归档 | 系统 | `DONE` → `CLOSED` |
| 12 | `CANCEL` | 撤销 | 学生 | `PENDING` / `ASSIGNED` → `CANCELLED` |

### 2.3 非转移事件（必须看清，否则会多加状态）

| 动作 | 是什么 | 为什么不占转移名额 |
|---|---|---|
| `REWORK_REQUEST` | 学生提交返修申请，原单仍为 `VERIFYING` | 只写审计事件和审查行，不改变状态 |
| `REWORK_REJECTED` | 管理员驳回误报申请，原单仍为 `VERIFYING` | 只写审计事件并重置 T1 |
| `ORIGIN_CLOSED`（级联） | 最终返修单验收通过时，原单及前序返修单从 `REWORKING` → `CLOSED` | `SYS-004` 第 8 条副作用，不占 13 条转移；记在学生头上，`manual=1` |
| `ADMIN_CANCEL`（缺口） | 师傅已进楼后学生申请撤销，管理员批准作废 | **`SYS-004` 里没有这条边**，目前返回 `501 CR-001` |

## 三、命令接口

> 每条命令统一结构：**端点 · 触发方 · 前置校验 · 请求 · 成功 · 失败 · 副作用**

### 3.1 建单 `SUBMIT`

```
POST /orders
角色：student
```

**请求**

```json
{
  "photoUrls": ["https://.../p1.jpg"],
  "desc": "洗手盆下面的软管一直滴水，水桶快接满了",
  "window": "晚上 18:00-22:00",
  "autoAssign": true
}
```

| 字段 | 必填 | 规则 |
|---|---|---|
| `photoUrls` | 是 | 至少 1 个；本期前端限制为 1 张 |
| `desc` | 是 | 去空格后 ≥ 4 字；≥ 500 字截断 |
| `window` | 否 | 取值见 `/meta`；不传 = `ALL`（全天） |
| `autoAssign` | 否 | 默认 `false`。为 `true` 时服务端在建单后立刻以 `system` 身份自动派工（本楼有当班师傅 → `ASSIGNED`，没有则留在 `PENDING`），返回体里直接带 `worker`。**这是"系统自动受理"的落地方式**：客户端不需要也不应该持有 system 身份 |

楼栋、寝室、手机号**不接受客户端传入**，由账号绑定关系带入；`category`、`level` 由服务端 AI 判定，客户端传了也忽略。

> 说明：`autoAssign` 不是新的一条转移，它只是在建单后追加一次标准的 `2 PENDING→ASSIGNED`（actor=`system`，`manual=0`）。不带这个字段时行为与旧版完全一致（返回 `PENDING`），所以接口测试里"建单必须仍是待派工"的断言不受影响。

**成功** `201`

```json
{
  "ok": true,
  "data": {
    "no": "BX20261117001",
    "status": "PENDING",
    "version": 1,
    "building": "B7", "room": "402",
    "window": "晚上 18:00-22:00",
    "ai": {
      "category": "给排水", "level": "紧急", "confidence": 0.98,
      "basis": "命中「滴水/软管」，归给排水；未命中安全类，保守不降级"
    },
    "createdAt": "2026-11-17 09:12:00"
  }
}
```

**失败**：`422`（照片为 0 / 描述不足 4 字 / 时段取值非法）

**副作用**
1. 生成单号（当日序号递增，`BX20261117001` 起）
2. 调 AI 定级：五类故障（给排水/电气/电器/门窗家具/网络）× 三档紧急（紧急/较急/普通）
3. AI 不可用（超时 3 秒或报错）→ 按「普通」入队，`ai.fallback = true`，**不允许因此拒单**
4. 写事件 `SUBMIT`，`manual = 1`
5. 同楼栋且时段重叠的单归入同一批次（批次号 `BT + 日期 + 楼栋 + 序号`）

---

### 3.2 派工 `ASSIGN`

```
POST /orders/{no}/assign
POST /buildings/{buildingId}/assign      ← 批量
角色：system
```

**前置**：`status = PENDING`；本楼栋有当班师傅。

**成功** `200`

```json
{ "ok": true, "data": { "assigned": true, "worker": { "id": "W0428", "name": "李建国" }, "version": 2 } }
```

**没派出去不是错误**：本楼栋无当班师傅时返回 `200` + `{ "assigned": false, "reason": "NO_WORKER_ON_DUTY" }`，工单留在 `PENDING`，进管理端例外清单。**不写事件、不改状态。**

**批量**返回逐单结果，允许部分成功：

```json
{ "ok": true, "data": { "ok": ["BX...001"], "failed": [{ "no": "BX...002", "reason": "NO_WORKER_ON_DUTY" }] } }
```

**副作用**：写 `workerId`、推送待办、写事件 `ASSIGN`，`manual = 0`。

### 3.3 打卡 `ARRIVE`

```
POST /orders/{no}/arrive
POST /buildings/{buildingId}/arrive      ← 楼栋打卡（一次点击，N 条单级事件）
角色：worker
```

**这是本项目最容易做错的一处，单独说明。**

师傅界面上只有一个「进楼打卡」按钮，点一次；但状态机是**单级**的（`SYS-004` 第 3 条）。所以服务端做的事是：

**一次请求 → 逐单校验 → 逐单生成 `ARRIVE` 事件**，每张单各自 `ASSIGNED → REPAIRING`，各自记录时间与操作人。

```json
// 请求
{ "buildingId": "B7" }

// 成功 200
{
  "ok": true,
  "data": {
    "arrivedAt": "2026-11-17 10:20:00",
    "ok": [
      { "no": "BX20261117002", "status": "REPAIRING" },
      { "no": "BX20261117003", "status": "REPAIRING" }
    ],
    "failed": [
      { "no": "BX20261117004", "code": 403, "message": "该工单不属于此师傅" }
    ]
  }
}
```

**规则**

| 项 | 约定 |
|---|---|
| 事务粒度 | **逐单独立事务**；一单失败不影响其他单（部分成功要如实返回，不能整体回滚） |
| 归属校验 | 每单 `workerId` 必须等于当前师傅，否则该单 `403` |
| 幂等 | 已 `REPAIRING` 的单跳过，计入 `skipped`，不报错 |
| 空批 | 本栋无待打卡单 → `200` + `{ "ok": [], "skipped": [] }` |

**副作用**（逐单）：写 `arriveAt`、通知学生「师傅已进楼」、写事件 `ARRIVE`，`manual = 1`。

> 撤销边界就挂在这里：`arriveAt` 一旦有值，学生不能再自己撤销，只能走「申请撤销」。

### 3.4 到访未遇 `NO_SHOW`

```
POST /orders/{no}/no-show
角色：worker
```

**请求**

```json
{ "reason": "KNOCK_NO_ANSWER", "note": "" }
```

`reason` 四选一（**只准选，不准打字**）：

| 值 | 显示 |
|---|---|
| `KNOCK_NO_ANSWER` | 敲门没人应 |
| `CALL_UNREACHABLE` | 电话打不通 |
| `STUDENT_NOT_IN` | 学生说不在寝室 |
| `DOOR_LOCKED` | 门反锁进不去 |

**前置**：本单属于当前师傅（`403`）；`reason` 在枚举内（`422`）。

**副作用**：清空 `workerId`、回 `PENDING`、该单「未遇次数」+1、**只影响这一单**（同批其他单照常）、写事件 `NO_SHOW`，`manual = 1`。

### 3.5 完工 `FINISH`

```
POST /orders/{no}/finish
角色：worker
```

**请求**

```json
{
  "photoUrls": ["https://.../after1.jpg"],
  "noteTags": ["REPLACED_HOSE", "TESTED_NO_LEAK", "CLEANED_FLOOR"],
  "note": ""
}
```

| 字段 | 必填 | 规则 |
|---|---|---|
| `photoUrls` | 是 | **至少 1 张**，本期固定 1 张 |
| `noteTags` | 是 | 至少 1 个，取自 `/meta` 的快捷说明枚举（免打字） |
| `note` | 否 | 自由文字，≤ 200 字 |

**前置**：本单属于当前师傅（`403`）；完工照 ≥ 1（`422`）；标签合法（`422`）。

**副作用**
1. 写 `finishAt`（**T1 计时起点**）
2. 通知学生验收
3. 写事件 `FINISH`，`manual = 1`

---

### 3.6 报缺件 `NEED_PARTS`

```
POST /orders/{no}/need-parts
角色：worker
```

**请求**

```json
{ "name": "衣柜合页 A2", "amount": 38, "etaDate": "2026-11-19" }
```

三个字段全必填（`422`）。`amount` 为数字，单位元，两位小数。

**副作用（关键：预算判断不改变工单状态）**

| 判断 | 采购状态 | 管理端 | 工单状态 |
|---|---|---|---|
| `amount ≤ budgetLine` | `ORDERED`（自动下单） | 不出现 | `PARTS` |
| `amount > budgetLine` | `PENDING_APPROVAL` | 进例外清单「超预算采购」 | **仍是 `PARTS`** |

写事件 `NEED_PARTS`，`manual = 1`。预算线默认 200 元，可配置。

---

### 3.7 配件到货 `PARTS_ARRIVED`

```
POST /orders/{no}/parts-arrived
角色：system | admin
```

**副作用**：回 `PENDING`、**保留原紧急度**（避免降级）、重新参与排队、写事件 `PARTS_ARRIVED`（管理员触发时 `manual = 1`，系统触发 `manual = 0`）。

---

### 3.8 验收通过 `ACCEPT`

```
POST /orders/{no}/accept
角色：student
```

**前置**：本单属于当前学生（`403`）。

**副作用**
1. 写 `signAt`（**T2 计时起点**）
2. `VERIFYING → DONE`
3. **级联**：若本单是返修单（有 `reworkOf`），把原单从 `REWORKING` → `CLOSED`，写事件 `ORIGIN_CLOSED`（记在学生动作上，`manual = 1`）
4. 写事件 `ACCEPT`，`manual = 1`

**响应**里要带上被关掉的原单：

```json
{ "ok": true, "data": { "no": "BX20261114001-R1", "status": "DONE", "closedOrigin": "BX20261114001" } }
```

---

### 3.9 申请返修 `REWORK_REQUEST`

```
POST /orders/{no}/rework-request
角色：student
```

请求：`{ "version": 4, "reason": "还在渗水，地面还是湿的" }`

**前置**：本单属于当前学生；状态为 `VERIFYING`；没有 `PENDING` 审查。`reason` 至少 2 个字。

**副作用**：写事件 `REWORK_REQUEST`；写 `t_rework_review(PENDING, attempt_no=下一轮, rework_index=NULL)`；工单状态和 `rework_index` 均不变；T1 暂停。

响应 `202`：

```json
{ "ok": true, "data": { "order": { "no": "BX20261118001", "status": "VERIFYING" }, "review": { "attemptNo": 1, "status": "PENDING" } } }
```

### 3.9.1 管理员审查返修 `REWORK_REVIEW`

```
POST /orders/{no}/rework-review
角色：admin
```

请求：`{ "version": 5, "decision": "APPROVE", "reason": "完工照显示接口未紧固，属于维修质量问题" }`

**APPROVE 副作用**：原单写 `REJECT` 并 `VERIFYING → REWORKING`；生成 `-R{n}` 的 `PENDING` 子单；审查行写 `APPROVED` 和 `rework_index`；第 2 次及以后写 `REPEAT_REWORK`。

**REJECT 副作用**：审查行写 `REJECTED`；原单保持 `VERIFYING`；写 `REWORK_REJECTED`；不生成新单；T1 从决定时刻重新计时。

响应：

```json
{ "ok": true, "data": { "original": { "no": "BX20261118001", "status": "REWORKING" }, "reworkOrder": { "no": "BX20261118001-R1", "status": "PENDING" } } }
```

驳回时 `reworkOrder` 为 null。

### 3.9.2 旧验收不通过接口（兼容）

`POST /orders/{no}/reject` 保留一期兼容，仍由学生调用并直接生成返修单；新 UI 不得再使用它。

### 3.10 超时自动验收 `AUTO_ACCEPT`

```
POST /orders/{no}/auto-accept
角色：system（内部定时任务，不对客户端开放）
```

**前置**：`status = VERIFYING` 且 `finishAt` 距今 ≥ `verifyHours`（默认 168 小时）。

**副作用**：写 `signAt`（取当前时间）、`DONE`、写事件 `AUTO_ACCEPT`（`manual = 0`，事件备注「学生 7 天未响应」）、T2 开始计时。

---

### 3.11 归档 `ARCHIVE`

```
POST /orders/{no}/archive
角色：system（内部定时任务）
```

**前置**：`status = DONE` 且 `signAt` 距今 ≥ `archiveDays`（默认 7 天）。

**副作用**：`CLOSED`、工单转只读（此后任何写接口一律 `409`）、写事件 `ARCHIVE`，`manual = 0`。

---

### 3.12 撤销 `CANCEL`

```
POST /orders/{no}/cancel
角色：student
```

**前置（两条同时满足）**

| 条件 | 不满足时 |
|---|---|
| `status ∈ {PENDING, ASSIGNED}` | `409`（`from`/`allowed` 一并返回） |
| `arriveAt` 为空 | `409`，message「师傅已进楼，不能撤销；请提交撤销申请」 |

**副作用**：清 `workerId`、`CANCELLED`、不进统计、写事件 `CANCEL`，`manual = 1`。

---

### 3.13 申请撤销（不是转移）

```
POST /orders/{no}/cancel-request
角色：student
```

**适用**：师傅已进楼（`REPAIRING`）、学生反悔。

**请求**：`{ "reason": "临时离校，不需要修了" }`

**行为**：**不改工单状态**，只在例外清单加一条「学生申请撤销」，等管理员处理。响应 `202`。

### 3.14 管理员作废（缺口，待变更单 #001）

```
POST /orders/{no}/admin-cancel
角色：admin
状态：⛔ 契约已起草，但 SYS-004 没有这条边 → 未过变更单前一律返回 501
```

## 八、实现约束（写代码时照着做）

1. **单一入口**：所有状态变更走 `StateMachine.transit(order, event, actor)`。业务代码里搜不到 `order.status = `。
2. **表驱动**：转移写成 `{ from, event } → to` 的映射表；表里没有的组合抛 `409`，**不写 if-else 兜底**。
3. **事务边界**：一次转移 + 它的事件写入 + 它的级联（`ORIGIN_CLOSED`、生成 `-R{n}`）在**同一个事务**内。
4. **批量允许部分成功**：楼栋打卡、批量派工逐单独立事务，返回 `ok` / `failed` / `skipped` 三组。
5. **`manual` 由 `actorType` 推导**，不接受客户端传入。
6. **时间只由服务端生成**，客户端传的时间一律忽略。
7. **照片先存对象存储再落 URL**，数据库只存 URL 字符串；单张压缩后 ≤ 500KB。
8. **只读终态**：`CLOSED` / `CANCELLED` 的任何写接口直接 `409`，不做特殊分支。

## 十一、前端对接约定（原型 → demo 不改页面）

原型现在用 `App.fire()` 本地推状态；接后端时只换一个文件：

```
assets/api.js
  submitOrder(payload)      → POST /orders
  assign(no)                → POST /orders/{no}/assign
  arriveBuilding(bid)       → POST /buildings/{bid}/arrive
  finish(no, payload)       → POST /orders/{no}/finish
  needParts(no, payload)    → POST /orders/{no}/need-parts
  accept(no) / reject(no, r) → POST /orders/{no}/accept|reject
  cancel(no)                → POST /orders/{no}/cancel
  cancelRequest(no, r)      → POST /orders/{no}/cancel-request
  listMine() / detail(no) / todo() / exceptions() / dashboard()
```

`api.js` 内部两种实现，由 `window.MOCK` 开关切换：`MOCK=1` 走本地状态机（现在的行为），`MOCK=0` 走 `fetch`。**页面代码一行不用改**，这是 P3 的门禁。

409 的展示已在原型里定好：红色提示块 + `code` + `from/event/allowed`。demo 阶段保持不变。
