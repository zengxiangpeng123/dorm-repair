宿舍维修流程 V5.0（全自动主干 · 可上门时段 · 监测式管理端）

这张图的核心只有一句：报修全程由系统自动推进，没有任何一张单需要人审批。V5.0 相对上一版的实质变化是学生多填一个「可上门时段」——有了它，「到访未遇」从一个只能事后登记的事故，变成一件事先能约掉的事；排队规则也随之从「一条混合权重」拆成「安全闸 / 截止时间 / 紧急度 / 先来先修」。管理端仍然不在主干上，只做两件事——看数据对不对、兜真正的例外。

主干零审批 三端：学生 / 维修 / 管理（+ 后台系统） 学生只填：照片 + 描述 + 可上门时段 3 条异常全部系统自动处理 两个「7 天」是两条不同的计时器 管理端三类例外都不占状态位

V5.0 补上的四处（相对 V3.1）

  • 补一个字段：学生报修多填「寝室什么时候有人」。闭环大纲里本来就有这一条，图上一直没画；它是「到访未遇」的事前解法——能约掉，就不必靠事后顺延
  • 拆开一条权重：原来「安全等级 → 楼栋合并 → 等待时长」是一条混合链，实现时只有一个生效。改成 安全闸 / 截止时间 / 紧急度 / 先来先修，楼栋降级为「攒批」而不是排序键
  • 分开两个 7 天：验收超时（进「已完成」）和完成后归档（进「已关闭」）原来是同一条边上的一个「7 天」，现在分别命名 T1 / T2
  • 说清例外位置：管理端三类例外都不占状态位，它们是标记和清单条目，工单状态照常推进

状态链（9 个状态 · 详见状态机图）

待派工 → 已派工 → 维修中 → 待验收 → 已完成 → 已关闭
旁路（自动回流，都回到「待派工」）：待配件（配件到货）· 返修中（生成 -R1 新单）
作废终态：已取消（学生撤销，只能撤到「师傅进楼」前）
不占状态的事件：到访未遇（回待派工）· 验收超时（→ 已完成）

两个「7 天」不是同一件事

  • T1 · 验收超时：待验收 停留满 7 天（168 小时）→ 系统自动确认完成，事件写「学生 7 天未响应」，从「完工提交」开始计时
  • T2 · 归档：已完成 之后满 7 天 → 系统归档为 只读并关闭工单，从「学生签字」开始计时
  • 两条都写满 7 天，起点不同、终点不同。合成一个计时器，会出现「刚签完字就被归档」或「永远不归档」

管理端只在三种情况被叫醒

  • 数据对不上：学生填的位置和宿舍台账不一致 （其余情况系统自动生效；工单照常生成）
  • 钱要花出去：配件超出预算额度，需要有人点头 （预算内自动下单；工单已在待配件，状态不变）
  • 同一单反复：连续 2 次验收不通过，说明不是手艺问题 （第一次自动返修；状态照常走返修中）

三类都不新增状态、不改在办工单的状态，只产生一条标记和一条清单记录。管理端唯一能改工单状态的地方在别处：维修中学生申请撤销，由管理员决定作废（→ 已取消）或补偿师傅。
