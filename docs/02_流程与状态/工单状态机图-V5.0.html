9 个状态 14 条合法转移 两条终态：已关闭 / 已取消 回流都回「待派工」 T1 验收超时 · T2 归档 撤销只到「进楼」为止

合法转移（14 条 · 触发方：学生 / 师傅 / 管理员 / 系统）

#事件触发方 从 → 到前置条件副作用
1SUBMIT学生— → 待派工照片 ≥ 1、描述 ≥ 4 字生成单号、AI 定级、写 toCalibrate
2ASSIGN系统待派工 → 已派工本楼栋有当班师傅写 workerId、推待办；没有当班师傅就停在待派工并进异常清单
3ARRIVE师傅已派工 → 维修中该单属于此师傅写 arriveAt、通知学生
4NO_SHOW师傅已派工 → 待派工选了 4 个原因之一清 workerId、顺延重排、计入「未遇次数」
5FINISH师傅维修中 → 待验收完工照 ≥ 1写 finishAt、通知验收，T1 开始计时
6NEED_PARTS师傅维修中 → 待配件缺件名 + 金额 + 预计日期预算内自动下单；超预算挂 ②
7PARTS_ARRIVED系统 / 管理员待配件 → 待派工—保留原 level、重新排队
8ACCEPT学生待验收 → 已完成—写 signAt，T2 开始计时；若是返修单则同时关掉原单
9REJECT管理员待验收 → 返修中填不通过原因生成 -R1 新单、原单挂起、紧急度升一档；第 2 次挂 ③
10AUTO_ACCEPT系统待验收 → 已完成T1 满 168 小时写 signAt，manual=0，事件标「学生 7 天未响应」
11ARCHIVE系统已完成 → 已关闭T2 满 7 天转只读，进归档与看板
12CANCEL学生待派工 → 已取消师傅还没接单工单作废，不进统计
13CANCEL学生已派工 → 已取消师傅还没进楼（未打卡）清 workerId，从该师傅待办中移除
14ADMIN_CANCEL管理员维修中 → 已取消学生已申请撤销，管理员填写决定原因记录批准人、决定原因，保留完整历史

必须被拒绝的转移（返回 409，不是静默忽略）

  • 待派工 → 维修中：跳过派工，师傅没有依据
  • 待派工 → 已完成：跳过整个维修过程
  • 已派工 → 待验收：没打卡就完工，时间线断了
  • 维修中 → 已完成：跳过学生验收
  • 待配件 → 已完成：缺件没换上就结单
  • 待验收 → 待派工：只能退成返修单，不能凭空回队
  • 维修中 + CANCEL：学生不能直接撤销，只能申请，由管理员通过 ADMIN_CANCEL 决定
  • 待验收 → 已取消：活已干完，只能验收或退回返修
  • 终态（已关闭 / 已取消）→ 任意：需要就重新报修
  • 非本单师傅执行 ARRIVE / FINISH，非本人执行 ACCEPT，或非管理员执行 REJECT：越权

图上 ①②③ 是什么

它们标的是管理端会被叫醒的位置。三个都不是状态，图上也没有对应的框。

  • 1 · 数据对不上：挂在 SUBMIT 上。学生填的位置和台账不一致时，工单照常生成、照常排队，管理端改台账，不动工单
  • 2 · 超预算采购：挂在 NEED_PARTS 上。金额超线时工单已经在待配件，批准与否只改「采购状态」，不改工单状态
  • 3 · 反复返修：挂在第 2 次 REJECT 上。工单照常走返修中 → 生成 -R1，管理端只判断根因

结论：三类例外都不占状态位。管理端读标记与清单，写台账与采购单。

需要管理员判断的转移：返修审查与批准撤销

学生撤销的边界不是技术限制，是成本：

  • 待派工 / 已派工（未打卡）→ 学生自己点撤销，零成本，走 CANCEL
  • 维修中（已进楼）→ 只能申请，进管理端例外处理台，由管理员决定作废或补偿师傅
  • 待验收 及之后 → 不能撤销，只能验收或退回返修

分界线就是「进楼打卡」：打卡前师傅还没出发，打卡后人已经在楼里。管理员只能通过返修审查 `REJECT` 和维修中撤销 `ADMIN_CANCEL` 改变状态，不能任意编辑工单。

两个 7 天，起点不同

  • T1 · 验收超时：起点是 FINISH（师傅交完工照），满 168 小时 → 已完成。防的是学生不验收把单子永远吊着
  • T2 · 归档：起点是 ACCEPT / AUTO_ACCEPT（签字时刻），满 7 天 → 已关闭。防的是单子停在已完成不归档，统计口径飘
  • 两条都叫「7 天」，合成一条会出两个 bug：刚签完字就被归档，或者一直不归档

为什么回流全部回到「待派工」

到访未遇、配件到货、返修新单，三条都回到 待派工，没有一条直接回 维修中。

原因：回「维修中」等于跳过派工直接插队，师傅会凭空多出一张没推送过的单，待办和实际作业对不上。回「待派工」才能重新参与排序、重新攒批；配件回流还要带上原紧急度，避免降级。
