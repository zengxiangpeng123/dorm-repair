## 一、迁移目标

迁移前基线为 10 张表；本次新增 6 张并已完成验收：`t_student`、`t_worker`、`t_admin`、`t_worker_building`、`t_building_floor`、`t_rework_review`。

迁移期保留 `t_user` 时为 16 张物理表；删除兼容视图和 `t_user` 后为 15 张。`v_user_account` 依赖 `t_user`，不能与 `t_user` 共存于“最终删除完成”状态。

## 二、前置检查

1. 备份数据库、`schema.sql`、`data.sql`。
2. 记录三类账号、师傅楼栋、楼栋楼层和返修链。
3. 保存工单状态分布、待验收/已完成单快照。
4. 在空库和副本库执行迁移。
5. 冻结“迁移期 16、最终 15”的表数口径。

## 三、迁移与删除顺序

| 步骤 | 操作 | 校验 |
|---:|---|---|
| 1 | 创建三类人员表 | 三表行数合计等于 `t_user` |
| 2 | 迁移账号、姓名、口令 | 每类账号抽 3 个登录 |
| 3 | 创建 `t_worker_building` | 每个师傅至少一条关系 |
| 4 | 创建 `t_building_floor` | 与旧 `floors` 逗号串逐项对账 |
| 5 | 创建 `t_rework_review` | 历史返修和审查可读 |
| 6 | 增加 `verify_due_at/archive_due_at` | 回填待验收和已完成单 |
| 7 | 创建 `v_user_account` 兼容视图 | 旧读取路径可用 |
| 8 | 切换 Repository 读写 | 建号、改口令、登录全通过 |
| 9 | 停写 `t_user` | 观察一个发布周期 |
| 10 | 删除 `v_user_account` 视图 | 确认已无读取依赖 |
| 11 | 删除 `t_user` 及 `t_building.floors` | 物理表数变为 15 |

**回滚窗口**：第 10 步之前可切回 `v_user_account`；视图或 `t_user` 删除后，回滚必须依赖数据库备份，不能再假装兼容视图可用。

## 四、Repository 读写路径

| 方法 | 目标行为 |
|---|---|
| `find(id)` | 按前缀或显式角色查 `t_student/t_worker/t_admin` |
| `all()` | 合并三表并转换为统一 `UserAccount` |
| `count()` | 三表行数求和 |
| `insert(UserAccount)` | 按 `role` 写入对应角色表 |
| `setPassword(id, hash)` | 按账号前缀查对应表并更新口令 |

兼容视图只承接过渡期读取；新增、改口令必须写角色表。

## 五、`floors` 删除的连带改造

删除 `t_building.floors` 前必须同步：

1. `app/server/src/main/resources/db/schema.sql`：移除 `floors` 列。
2. `app/server/src/main/resources/db/data.sql`：改为写入 `t_building_floor` 行。
3. `MetaController`：`/meta` 的 `buildings[].floors` 从 `t_building_floor` 读取，删除硬编码楼层。
4. 迁移对账：B7/B8 楼层逐项一致。

前三处任意一处未改，会导致 `/demo/reset` 或 `/meta` 失败或出现第二份事实来源。

## 六、返修审查轮次

### 6.1 表结构

`t_rework_review`：

- `id`
- `order_no`
- `attempt_no`：同一原单的申请轮次，从 1 递增
- `rework_index`：批准后生成的第几次返修，申请时为 NULL
- `status`：`PENDING/APPROVED/REJECTED`
- `requested_by`
- `request_reason`
- `requested_at`
- `decided_by`
- `decision_reason`
- `decided_at`

约束：

- `UNIQUE(order_no,attempt_no)`：每次申请一轮，历史不覆盖。
- `UNIQUE(order_no,rework_index)`：MySQL 允许多个 NULL；批准后同一返修轮次只能有一条。

### 6.2 流程

- 学生申请：插入新 `attempt_no`，`rework_index=NULL`，`PENDING`。
- 管理员驳回：该行改为 `REJECTED`，不生成子单；再次申请插入新 `attempt_no`。
- 管理员批准：该行改为 `APPROVED`，写入下一个 `rework_index`，生成 `-R{n}`。
- 不允许通过更新旧驳回行来覆盖历史。

## 七、T1 暂停与恢复

- 申请时：原单保持 `VERIFYING`，存在 `PENDING` 审查则跳过 T1。
- 批准后：原单进入 `REWORKING`，T1 终止。
- 驳回后：从决定时间重新计算并写回 `verify_due_at`。
- `TimerService` 必须同时读取审查表和 `verify_due_at`，不能只改扫描条件。

## 八、自动派工最小方案

- 只按工单楼栋查询 `t_worker_building`。
- 优先 `is_primary=1` 的当班师傅。
- 本期不做故障类别与班组映射。
- 找不到师傅：工单保持 `PENDING`，手动 `/assign` 返回 `422 NO_WORKER_AVAILABLE`，不新增例外类型。
- 删除对 `W0428` 的硬编码回退。

## 九、回滚与退出

- 视图和 `t_user` 删除前：可切回兼容视图与旧 mapper。
- 删除后：只能恢复数据库备份；新表数据不主动删除。
- 退出条件：16/15 表数一致、五类 Repository 方法通过、审查轮次历史正确、T1 三态和自动派工测试通过。
